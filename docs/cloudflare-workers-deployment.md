# Deploy OpenKuasa to Cloudflare Workers (fork: wings105)

## Scope

This branch configures **vinext** as an alternative build for the existing Next.js 16 App Router application. The original `pnpm dev`, `pnpm build`, Netlify config, Supabase integrations and source routes are retained. Nothing here automatically deploys or migrates production data.

The original `npx wrangler deploy` failed because it attempted an interactive OpenNext migration inside Cloudflare CI, and pnpm 11 blocked previously unapproved native build scripts. Do not use that deploy command for this branch.

## Verified so far

- Cloudflare's original `next build` completed with `NODE_OPTIONS=--max-old-space-size=4096`.
- GitHub Actions executed `pnpm dlx vinext check` on this fork. The check reported 10/10 supported imports, 4/4 supported config options, 3/3 compatible libraries, and 100% overall compatibility (0 partial, 0 issues).
- `vinext init` generated `vite.config.ts`, `cloudflare.config.ts` and namespaced build/deploy scripts. The lockfile was updated and `esbuild` / `workerd` were explicitly approved in pnpm's `allowBuilds` policy.
- **Important:** a static compatibility check does *not* prove Cloudflare runtime behavior. Confirm that the vinext build succeeds and separately smoke-test middleware/proxy, CSP nonce, Next.js Server Actions, routes, auth cookies, images, and uploads.

## Build and deploy through Cloudflare Workers Builds

Connect branch `fix/cloudflare-workers-deploy` for an isolated preview (or merge to `main` only after reviewing and validating it).

| Cloudflare setting | Value |
| --- | --- |
| Root directory | `/` |
| Build command | `pnpm run build:vinext` |
| Deploy command | `pnpm exec vinext-cloudflare deploy --skip-build` |
| Build variable | `NODE_OPTIONS=--max-old-space-size=4096` |
| Build/runtime Node | Node.js 24 (22+ is supported by original app) |

The deploy command uses the Cloudflare-native adapter generated by `vinext init`, not the auto-migrating `npx wrangler deploy` fallback. If your Cloudflare Build runtime does not already provide deployment authorization, configure `CLOUDFLARE_ACCOUNT_ID` and a securely stored `CLOUDFLARE_API_TOKEN` with the minimum Workers edit permissions necessary; do not commit tokens or server-side keys.

The generated config defines a Worker named `openkuasa`. No KV or Cloudflare Images service is provisioned by this initial migration; these may be configured later. The vinext deployment CLI and Cloudflare platform interfaces can change; check current Cloudflare build logs before assuming a failed deploy is an app problem.

### Preview/demo mode (before connecting Supabase)

To view sample data **without database access**, configure the Worker **runtime environment variable**:

```env
OPENKUASA_PREVIEW=1
```

Do **not** add production Supabase URL/key pairs to this demo deployment. Preview users see read-only sample content. Without Supabase credentials and without `OPENKUASA_PREVIEW=1`, the app intentionally returns HTTP 503 in production. Never use the preview flag as a substitute for authentication on a real data deployment.

### Production database later

Use a **separate Supabase project** for OpenKuasa, never the existing iCetak production database. Run and review `pnpm db:migrate` and `pnpm db:migrate --apply` explicitly against that project only after confirming its ID and backups. Supply the official environment variables from `.env.example` in Cloudflare's protected environment/secrets UI, including the Supabase server-only service-role key and encryption secret where required. Do not prefix server-only secrets with `NEXT_PUBLIC_`.

Configure Cloudflare runtime env and Supabase Auth callback URL for the actual domain before testing registration/login, cookie renewal, password reset and external authentication. Configure scheduled agents separately; they are **disabled by default** and require `AGENTS_ENABLED=true` and `CRON_SECRET`.

### Smoke test before enabling real data

1. Open the Worker `*.workers.dev` URL and confirm it renders the preview dashboard, login redirect behavior, and several CRM/HR/Finance pages without JavaScript errors.
2. Verify middleware session refresh and CSP nonce/security headers on public and authenticated pages; observe browser console for blocked hydration/scripts.
3. Test API routes with safe sample requests and confirm that server actions, image rendering, form validation and file uploads work correctly. Image optimization is **not** configured yet, so treat image resizing as a separate requirement.
4. Review build logs and Worker Observability before attaching a custom domain.
5. Confirm a rollback is possible to the previously working Worker version if the new deploy fails.

## Development workflow

Keep code changes on short-lived branches and use PRs. The compatibility audit workflow runs on the dedicated deployment branch. A one-time bootstrap workflow generated this adapter in GitHub Actions; it is intentionally guarded against overwriting existing `vite.config.ts` or `cloudflare.config.ts`.

### Known limitations

- vinext's compatibility check is static; behavioral parity for this specific app is not yet established.
- OpenKuasa itself is early-stage software and its README identifies modules still using sample data or missing external integrations.
- AGPL-3.0 license conditions remain applicable when serving a modified version over a network.
- Deployment credentials, custom domain setup, database migrations and live Worker smoke tests are operational tasks, not handled automatically by the GitHub PR.

Official reference: https://vinext.dev/docs/deploying/cloudflare and https://github.com/cloudflare/vinext.
